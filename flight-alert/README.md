# バグ価格アラート（羽田・成田発）

羽田・成田発の航空券を定期的に見張って、**普段の相場からありえないほど安い運賃**が
出たときだけスマホに通知するツールです。羽田-ロサンゼルス往復4万円のような、
数十分で消えるエラーフェアを見逃さないことを狙っています。

通知にはその日程の **Skyscanner 検索ページへの直リンク**が入るので、
届いた通知をタップすればそのまま Skyscanner で確認・購入できます。

通知は**既定でメールに届きます**（Discord / Slack / Telegram にも切り替えられます）。

```
🚨 HND→LAX 往復 ¥39,800
日程: 2026/04/15（水）発 → 04/22（水）帰り・7泊
便: 航空会社 JL / 直行便
相場: 直近30日の中央値 ¥168,000
判定: 通知ライン超え、相場割れ、統計的な外れ値
　・設定した通知ライン ¥60,000 を下回りました（¥20,200 安い）
　・直近30日の相場 ¥168,000 に対して 76%オフ
　・普段の値動きの幅（±¥8,000）から見て 10.8σ 下振れしています

Skyscannerで確認: https://www.skyscanner.jp/transport/flights/hnd/lax/260415/260422/...
```

---

## はじめに：なぜ Skyscanner を直接監視しないのか

**Skyscanner には誰でも使える公開 API がありません。**
提供されているのは提携企業向けの B2B API のみで、個人が申し込んで使えるものでは
ありません。サイトを直接スクレイピングする方法は利用規約に違反するうえ、
Bot 対策が強力なので、動いたとしてもすぐ止まります。

そこでこのツールは役割を2つに分けています。

| 役割 | 使うもの |
|---|---|
| 価格を**見張る** | 正規に使える価格 API（Travelpayouts ほか） |
| 価格を**確認して買う** | Skyscanner（通知内の直リンクから） |

見張りは API に任せ、通知が来たら Skyscanner で買う。この形なら規約の範囲内で、
体感は「Skyscanner のバグ価格通知」と同じになります。

---

## 仕組み

1. 30分おきに、羽田・成田発の各路線・各月の最安値を取ってくる
2. 「その日その路線の最安値」を SQLite に貯めて、**路線ごとの相場**を作る
3. 次の3つのどれかに当たったら通知する

| ルール | 内容 | いつから効くか |
|---|---|---|
| `absolute` | 行き先ごとに決めた金額（例：北米往復6万円）を下回った | **初日から** |
| `baseline` | 直近の相場（中央値）の半額以下になった | 履歴が8日ぶん貯まってから |
| `outlier` | 中央値からのばらつき（MAD）で見て 4σ 以上の下振れ | 履歴が8日ぶん貯まってから |

`absolute` があるおかげで、動かした初日からバグ価格には気づけます。
`baseline` と `outlier` は履歴が育つほど賢くなり、
「元が安い路線の異常値」や「セール価格との違い」を見分けられるようになります。

誤検知を減らすための工夫:

- 相場の計算に**当日ぶんは含めない**（バグ価格が自分で相場を下げてしまうのを防ぐ）
- 平均ではなく**中央値と MAD** を使う（1回の異常値に相場が引っ張られない）
- `outlier` は「中央値の70%以下」でないと発火しない（値動きが小さい路線での過敏な反応を防ぐ）
- 同じ便は `cooldown_hours` の間は再通知しない。ただし価格を1000円単位に丸めた値が
  下がれば別物として扱い、**さらに安くなったときは通知し直す**
- 1回の実行で送る通知は `max_alerts_per_run` 件まで

## 5分で試す（APIキー不要）

```bash
cd flight-alert
cp config.example.json config.json
python -m bugfare demo -c config.json
```

サンプルの価格データで、検知から通知文面までの流れがそのまま画面に出ます。
Python 3.9 以降なら追加インストールは不要です（**外部ライブラリを一切使いません**）。

## 本番セットアップ

### 1. 価格 API のトークンを取る

**Travelpayouts** — 無料。1リクエストで1か月ぶんのカレンダー最安値が返るので、
多くの路線を広く見張るのに向いています。

1. <https://www.travelpayouts.com/> に登録する
2. 管理画面（Profile → API token）でトークンを控える
3. `TRAVELPAYOUTS_TOKEN` に設定する

> ⚠️ **Travelpayouts は本来アフィリエイト提携先向けのサービスです。**
> 登録直後に「自分のサイトに Drive スクリプトを設置して検証する」設定案内が始まり、
> **これを完了するまで管理画面全体がロックされ、API トークンの画面にも入れません。**
> 実際に運用しているサイトを持っていない場合、ここで詰まります。

**Amadeus** — `provider.name` を `"amadeus"` にすると使えますが、
**個人向けの Self-Service ポータルは 2026年7月17日に廃止されました。**
新規登録は停止され、既存のキーも無効化されています。実装は残してありますが、
Amadeus Enterprise の契約がある場合を除き、**新たに使い始めることはできません。**

### 2. 通知先を用意する

**既定はメール通知です。** 追加のアプリを入れなくても、スマホのメールアプリが
そのまま知らせてくれます。

#### メール（既定）

Gmail の場合、**普段のログインパスワードでは送れません。** 2段階認証を有効にした
うえで「アプリパスワード」を発行し、それを使います。

1. Google アカウント → セキュリティ → **2段階認証プロセス**を有効にする
2. 同じ画面の **アプリ パスワード** から、16桁のパスワードを発行する
   （直接開く場合は <https://myaccount.google.com/apppasswords>）
3. 発行された16桁を控える（スペースは入れても入れなくても構いません）

必要な設定は2つだけです。

| 環境変数 | 中身 |
|---|---|
| `SMTP_USERNAME` | 送信に使う Gmail アドレス |
| `SMTP_PASSWORD` | 上で発行した16桁のアプリパスワード |

`ALERT_EMAIL_TO`（宛先）は**省略できます。** 省略すると `SMTP_USERNAME` と同じ
アドレス、つまり自分宛に届きます。別のアドレス（キャリアメールなど）で
受け取りたいときだけ設定してください。

Gmail 以外を使う場合は `config.json` の `host` と `port` を変えます。

| 送信元 | host | port |
|---|---|---|
| Gmail | `smtp.gmail.com` | `587` |
| Outlook / Hotmail | `smtp-mail.outlook.com` | `587` |
| Yahoo!メール | `smtp.mail.yahoo.co.jp` | `465` |

`port` に `465` を指定すると SSL 接続、それ以外は STARTTLS で接続します。

#### 別の通知先に変えたい場合

`config.json` の `notifiers` で、使いたいものの `enabled` を消すか `true` にし、
使わないものに `"enabled": false` を付けます。複数を同時に有効にもできます。

- **Discord** … サーバー設定 → 連携サービス → ウェブフック → 新しいウェブフック → URLをコピー。プッシュが速いのが利点です
- **Slack** … Incoming Webhook の URL を `webhook_url` に入れます
- **Telegram** … BotFather でボットを作り、そのボットに一度話しかけてから `https://api.telegram.org/bot<トークン>/getUpdates` で `chat_id` を調べます
- **webhook** … 任意の URL に JSON を POST します。LINE Messaging API の自作サーバーなどに流したいとき用です

> LINE Notify は2025年3月末で終了しているため、対応していません。

### 3. GitHub Actions で自動実行する

このリポジトリの `.github/workflows/flight-alert.yml` が30分おきに実行します。
リポジトリの Settings → Secrets and variables → Actions に、使うものだけ登録します。

| Secret 名 | 用途 | |
|---|---|---|
| `TRAVELPAYOUTS_TOKEN` | 価格取得 | **必須** |
| `SMTP_USERNAME` | 送信に使うメールアドレス | **必須**（既定のメール通知） |
| `SMTP_PASSWORD` | アプリパスワード | **必須**（既定のメール通知） |
| `ALERT_EMAIL_TO` | 宛先を自分以外にしたいとき | 任意 |
| `DISCORD_WEBHOOK_URL` | Discord 通知に切り替えるとき | 任意 |
| `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` | Telegram 通知に切り替えるとき | 任意 |

`config.json` には `"${TRAVELPAYOUTS_TOKEN}"` のような**環境変数の参照しか書きません**。
秘密が入らないので、そのままコミットして構いません。

価格履歴の SQLite は `actions/cache` で実行間に持ち越しています。
キャッシュが飛ぶと相場のやり直しになりますが、`absolute` ルールは動き続けます。

> GitHub の cron は混雑時に数分〜十数分遅れます。分単位の速さが要るなら、
> 手元のマシンや VPS の cron で回すほうが確実です:
> `*/15 * * * * cd /path/to/flight-alert && /usr/bin/python3 -m bugfare scan -c config.json`

### 4. 配線を確認する

```bash
export TRAVELPAYOUTS_TOKEN=...
export SMTP_USERNAME=あなたのアドレス@gmail.com
export SMTP_PASSWORD=16桁のアプリパスワード

python -m bugfare test-notify -c config.json      # 通知先にテスト1通を送る
python -m bugfare scan -c config.json --dry-run   # 実データを取るが通知はしない
```

`test-notify` を実行して受信箱に
**「[バグ価格] HND→LAX ¥30,000」** のような件名のメールが届けば、配線は完了です。
届かない場合は迷惑メールフォルダを確認してください。

GitHub Actions 上で試すときは、Actions タブから
**「バグ価格チェック」→ Run workflow** で手動実行できます。送信に失敗した場合は
その実行が赤いバツで終わり、ログに理由が出ます（黙って止まることはありません）。

## コマンド

| コマンド | 内容 |
|---|---|
| `scan` | 価格を取得し、条件に合えば通知する（定期実行するのはこれ） |
| `scan --dry-run` | 実データを取るが、通知は送らず画面に出すだけ |
| `demo` | APIキーなしで、検知と通知文面の流れを確認する |
| `test-notify` | 通知先にテストの1通を送る |
| `stats` | 貯まっている相場と直近の通知を一覧する |
| `prune --keep-days 180` | 古い履歴を捨てる |

`stats` の出力例:

```
路線                            日数      中央値       25%点        直近
------------------------------------------------------------------------
HND-LAX:round:2026-04             23    ¥168,000    ¥151,000    ¥163,400
HND-LAX:round:2026-05              6    ¥172,500    ¥160,000    ¥170,000  相場計算まで待ち
```

## 設定リファレンス（`config.json`）

### `search`

| キー | 既定 | 内容 |
|---|---|---|
| `origins` | `["HND","NRT"]` | 出発空港。`TYO` で東京の全空港をまとめて見ることもできます |
| `trip_types` | `["round","oneway"]` | 往復・片道のどちらを見るか |
| `months_ahead` | `6` | 何か月先まで見るか。**増やすとリクエスト数が比例して増えます** |
| `min_days_ahead` | `3` | 明日発など、間に合わない日程を除外する |
| `limit_per_query` | `30` | 1回の問い合わせで受け取る件数 |
| `direct_only` | `false` | 直行便だけに絞るか |

リクエスト数は `出発地 × 行き先 × 月数 × 往復/片道` です。
既定の設定（2 × 26 × 6 × 2 = 624）は `provider.max_requests`（400）で頭打ちになるので、
全部見たい場合は行き先か月数を減らすか、`max_requests` を上げてください。

### `targets`

監視する行き先のまとまり。`alert_price` が実質の「通知ライン」です。

```json
{
  "name": "北米・ハワイ",
  "destinations": ["LAX", "SFO", "SEA", "JFK", "ORD", "YVR", "HNL"],
  "alert_price": 60000,
  "oneway_alert_price": 35000,
  "drop_ratio": 0.4,
  "enabled": true
}
```

- `alert_price` … 往復でこの額以下なら即通知（省略可）
- `oneway_alert_price` … 片道でこの額以下なら即通知（省略可）
- `drop_ratio` … この行き先だけ相場ルールのしきい値を変える（省略時は全体の設定）
- `enabled` … `false` で一時的に止める

**最初は通知ラインをやや厳しめ（安め）に設定してください。** 通知が来なさすぎると
感じたら徐々に上げるのが、慣らし方としてはうまくいきます。

### `detection`

| キー | 既定 | 内容 |
|---|---|---|
| `drop_ratio` | `0.5` | 相場の何割以下で通知するか。`0.4` にすると6割引以上だけ |
| `min_samples` | `8` | 相場を信用するのに必要な日数 |
| `lookback_days` | `60` | 相場を計算する期間 |
| `mad_sigma` | `4.0` | 外れ値ルールの厳しさ。下げると通知が増える |
| `min_price_jpy` | `3000` | これ未満はデータ不良として捨てる |

### `alerting`

| キー | 既定 | 内容 |
|---|---|---|
| `cooldown_hours` | `12` | 同じ便を再通知しない時間 |
| `max_alerts_per_run` | `10` | 1回の実行で送る上限 |
| `price_bucket_jpy` | `1000` | 同じ便かどうかを判定するときの価格の丸め単位。細かくすると再通知が増える |
| `adults` | `1` | Skyscanner リンクに入れる人数 |
| `cabin_class` | `"economy"` | `economy` / `premiumeconomy` / `business` / `first` |

## 通知が来たときにやること

エラーフェアは表示されてから消えるまでが早く、確保できても後から取り消される
ことがあります。実務的には次の順で動くのが安全です。

1. **すぐ買う。相談や比較は後**（数十分で消えます）
2. 航空会社の公式サイトか、通知内の Skyscanner リンクから買う
3. **発券（eチケット番号の発行）まで確認する**。予約番号だけでは確定ではありません
4. 発券後も、航空会社が「システム上の誤りによる運賃」として取り消す場合があります。
   取り消しは発券から数日以内に来ることが多いので、**しばらくはホテルなど他の予約を
   確定させない**
5. 予約内容の変更や座席指定はしばらく触らない（再計算で運賃差額を請求されることがあります）

## 制約と注意

- **価格データには遅れがあります。** Travelpayouts が返すのは各社の検索結果を集計・
  キャッシュしたもので、実売と数十分〜数時間ずれることがあります。通知が来ても
  Skyscanner 側では既に売り切れている、ということは普通に起きます。
  逆に、この遅延ぶんだけ「もう消えた運賃」を掴む可能性もあります。
- **全部のバグ価格は拾えません。** 監視できるのは設定した路線・月のカレンダー最安値
  だけです。特殊なクラスや発券地の組み合わせで発生するタイプは検知できません。
- **GitHub Actions の cron は遅れます。** また、リポジトリが60日間更新されないと
  スケジュール実行が自動停止します。
- Skyscanner のスクレイピングは行いません（規約違反かつ実用にならないため）。
- このツールは価格の異常を知らせるだけで、**購入した運賃が有効であることを保証しません。**

## 開発

```bash
cd flight-alert
python -m unittest discover -s tests -t .
```

外部依存はありません。標準ライブラリのみで動きます。

```
flight-alert/
├── bugfare/
│   ├── cli.py            # コマンドの入り口
│   ├── config.py         # 設定の読み込みと検証
│   ├── models.py         # Offer / Alert などのデータ構造
│   ├── store.py          # SQLite。価格履歴と相場の計算
│   ├── detector.py       # 3つの判定ルール
│   ├── links.py          # Skyscanner / Google フライトへの直リンク
│   ├── http.py           # 標準ライブラリだけの HTTP クライアント
│   ├── providers/        # 価格の取得元（travelpayouts / amadeus / sample）
│   └── notifiers/        # 通知先（discord / slack / telegram / email / webhook / console）
├── tests/
├── config.example.json
└── README.md
```

新しい取得元や通知先を足すときは、それぞれ `Provider` / `Notifier` を継承したクラスを
1つ書いて、`providers/base.py` または `notifiers/base.py` の登録表に追加するだけです。
